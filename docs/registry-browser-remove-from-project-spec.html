Registry Browser — Remove from Project

Specification  |  Version 0.4  |  2026-07-29

1. Problem

Embedded packages (cloned into Packages/Embeds/{id} with a file:Embeds/{id} manifest entry) currently expose only De-embed in the Registry Browser window. De-embed deletes the local clone and reverts the manifest to a registry version.

There is no way to remove an embedded package from the project entirely — i.e. delete the local clone and remove the dependency line from Packages/manifest.json without reinstalling a registry version.

Additionally, the MCP tool currently has no removal action at all for registry-installed packages, even though the UI does.

2. Goal

Reuse the existing Remove from project button for embedded packages, branch the handler by package state, and expose a single MCP action that removes both registry-installed and embedded packages from the project.

3. Scope

In scope

  • Reuse the existing Remove from project button in PackageDetailPanel for Embedded packages.
  • Branch the button handler by package status: registry-installed packages keep using Client.Remove; embedded packages use the new removal path.
  • Add RegistryBrowserAPI.RemoveFromProjectAsync(string packageId, bool force = false) API that works for both InstalledFromRegistry and Embedded packages.
  • Add remove_from_project action in the MCP tool, with an optional Force parameter for embedded packages.
  • Safety checks for embedded path: locked files always block; uncommitted changes block unless force = true.

Out of scope

  • Changing De-embed behavior.
  • Adding a second button; the existing button is reused.
  • Removing local-only packages via this action (still handled by the existing Delete package button / separate MCP concern).

6. API Additions

A single new API call handles both registry-installed and embedded removal.

// RegistryBrowserAPI.cs
public static async Task RemoveFromProjectAsync(string packageId, bool force = false)
{
    if (string.IsNullOrWhiteSpace(packageId))
        throw new ArgumentException("Package ID cannot be empty.", nameof(packageId));

    if (GitEmbedOperations.IsEmbedded(packageId))
    {
        if (GitEmbedOperations.IsEmbedDirectoryInUse(packageId, out string lockedFile))
            throw new InvalidOperationException(
                $"Cannot remove: the package directory has locked files ({Path.GetFileName(lockedFile)}). " +
                "Close any applications accessing the package and try again.");

        if (!force && GitEmbedOperations.HasGitRepo(packageId))
        {
            bool hasChanges = await GitEmbedOperations.EmbedHasChangesAsync(packageId);
            if (hasChanges)
                throw new InvalidOperationException(
                    "Cannot remove: the package has uncommitted local changes. " +
                    "Commit or discard changes before removing, or use force.");
        }

        await GitEmbedOperations.RemoveEmbedAsync(packageId);
        PackageManifestEditor.RemoveDependency(packageId);
        return;
    }

    // Registry-installed package: use Unity Package Manager.
    var apiClient = new RegistryApiClient();
    await apiClient.RemovePackageAsync(packageId);
}

For embedded packages the call mirrors DeEmbedAsync but calls RemoveDependency instead of SetRegistryVersion. The force parameter only affects the uncommitted-changes check; locked files always block. For registry packages it delegates to the existing Client.Remove path and force is ignored.

8. Consequences & Risks

Data loss: Remove from project permanently deletes the Packages/Embeds/{id} directory. With force = true any uncommitted work is lost. The UI warns; the MCP caller must opt in explicitly.
Dependency breakage: Unlike Client.Remove for registry packages, the embedded path directly edits the manifest and does not validate whether other installed packages depend on the removed one. This is consistent with existing De-embed / Delete-local behavior but must be documented.
Package release chain: The change touches two published packages:
  1. com.warlogic.registrybrowser — API + UI changes. Bump version (e.g. 1.7.0 → 1.8.0).
  2. com.warlogic.registrybrowser.mcp — new action. Bump version (e.g. 2.0.0 → 2.1.0) and update its dependency on com.warlogic.registrybrowser to the new version.
DeedPlanner's Packages/manifest.json and Packages/packages-lock.json must then be updated to consume the new versions.
Git hook: The pre-commit hook that blocks commits while packages are embedded will naturally stop applying once the embedded directory is gone.

10. Verification Checklist

  • Existing "Remove from project" button is visible for embedded packages.
  • Clicking it for an embedded package with no local changes succeeds.
  • Clicking it for an embedded package with local changes shows a warning; cancel aborts, discard removes.
  • Operation deletes the embed directory and removes the manifest dependency.
  • Locked files block the operation with a clear error, even when force is used.
  • Existing "Remove from project" button still works for registry-installed packages.
  • MCP remove_from_project succeeds for a clean embedded package.
  • MCP remove_from_project fails for an embedded package with uncommitted changes unless Force=true.
  • MCP remove_from_project succeeds for a registry-installed package.
  • De-embed still works exactly as before.
  • Delete-package for local-only packages still works.

11. Assumptions

  • The canonical source for com.warlogic.registrybrowser is the external repository https://github.com/Warlander/registry-browser.git; changes must be published as a new package version.
  • DeedPlanner consumes registry-browser through the scoped UPM registry, not through an embedded copy in this repo.
  • The requested feature applies to both the editor UI and the MCP tool.
